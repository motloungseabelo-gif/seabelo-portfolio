Why I build

The repository is the evidence. This page explains the reason.

I use projects to test ideas and improve judgment. For each one, I want you to understand the problem that interested me, the decision I was trying to make and what I learned from building it.

Open GitHubDiscuss my work
SBM ConTech IndustriesWeb · product thinking

Why I built it: to learn how a technical company earns trust before a conversation starts.

A business website can become a list of services very quickly. I wanted to work on the harder question: how should a technology company explain itself so a visitor understands its direction, feels confidence in the brand and can move through the site without unnecessary friction?

The problem I exploredTechnical companies often communicate in a way that sounds impressive but leaves the visitor unsure what the company actually does.
The decisions that matteredInformation hierarchy, mobile behaviour, restrained motion, loading performance, contact flow and keeping visual ambition from competing with clarity.
What I learnedFront-end work is not only styling. Performance, accessibility and communication are part of the engineering decision.

SpendwiseAndroid · personal finance

Why I built it: because money is harder to manage when the consequences stay invisible.

I was interested in how an app could make day-to-day spending easier to see before it becomes a month-end surprise.

The questionHow can a user understand what is left, what is changing and whether a goal is still realistic?
The learningFinancial interfaces need clear state, sensible categories and data that helps a person decide—not just dashboards that look attractive.

Kayak DatabaseOracle SQL · data modelling

Why I built it: to understand how good interfaces depend on good relationships underneath.

I wanted to get closer to the data layer and understand how customers, kayaks, upgrades and access rules should relate before an application can behave reliably.

The questionWhat breaks later if the data model is unclear at the beginning?
The learningRelationships, constraints and access decisions are architecture choices. A clean UI cannot compensate for unreliable data structure.

FocusFlow JSJavaScript · interaction

Why I built it: to learn browser behaviour through something that needed interaction, not just layout.

I used a productivity idea as a reason to practise JavaScript state and page interaction. The goal was to make the interface respond to a user rather than remain a static presentation.

The questionHow should the interface communicate what changed after a user action?
The learningFront-end logic becomes easier to reason about when state changes are explicit and the interface gives immediate feedback.
